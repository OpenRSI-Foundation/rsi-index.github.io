Contribute

How to contribute a task.

Every contribution follows the same idea: identify a bounded, researchable experiment inside an influential open project, and turn it into a verifiable RSI environment. An automated pipeline handles most of the mechanical work; contributors provide the idea and review the results.

The fast path

From an idea to a validated task in about thirty minutes of active work.

The contribution pipeline is automated end to end: agents draft the proposal, review it, build the Harbor package, and run the checks — you review and confirm. It lives in RSI-Index-Public; the README there is the canonical guide.

01 · PROPOSE

Draft with proposal-agent

Clone RSI-Index-Public, open it in Codex, and ask for the proposal-agent skill. It walks the research question, baseline, evaluation, scope, and compute requirements, then generates a complete RSI task proposal for your review.

02 · SUBMIT

Post it as a Task-Ideas Discussion

Create a new Discussion in the Task-Ideas category and paste the proposal in. An automated review responds; edit the same Discussion until the proposal is accepted.

03 · BUILD

Let the bot create the task

In the accepted Discussion, drive task creation with slash-commands — each posted as a new comment. When you confirm, a private, ready-to-use task repository is created for you.

04 · VALIDATE

Run the validator if you have GPUs

Clone your private task repository on a machine with the required GPUs, run the bundled harbor-task-validator skill, and upload the validation logs. GPU-validated contributions receive more credit; without GPUs, leave feedback and you're done.

# in the accepted Task-Ideas Discussion — each command as a new comment
/task              # start task preparation
/task <feedback>   # revise the drafted task
/task confirm      # approve — creates your private task repository
/reset             # discard the attempt before repository creation

Two starting points

PATH A

Bring a project you coauthored

Contribute a high-impact project you helped build, provided it satisfies the project-selection gates below. You know its open research directions, and its reward-hacking risks, better than anyone else.

PATH B

Adopt a project from the taxonomy

Select an existing project from the track list that is closely aligned with your domain expertise, and design a new RSI task around it.

Project gates

GateRequirement
Fully openEverything necessary for the chosen lane is public and usable: runnable code, configuration, required model/checkpoint and data assets, and an evaluation path.
InfluentialThe project materially shaped its cohort through adoption, citations, community use, or an important open release.
ReproducibleThe author-released path can run end to end in a documented environment. Missing assets, broken execution, or a metric that cannot be independently checked stop admission.
ResearchableIt exposes a meaningful open research space in which the agent's research decisions affect the result.
VerifiableA separate verifier can evaluate the final artifact with fixed metrics and integrity constraints.

Under the hood

Six steps from open project to RSI task.

This is the full contract the fast-path automation drives for you — and the checklist for anyone designing and validating a task by hand.

Select a project

Choose either a high-impact project you coauthored that meets the gates, or a project from the taxonomy that matches your expertise. Identify its author-released repository and the assets required for the proposed experiment.

Identify a scientifically meaningful autoresearch lane

Choose a bounded experiment that gives the agent meaningful research decisions and a fixed, measurable objective. Avoid lanes whose main challenge is only engineering parameter search — prefer problems with the potential to produce genuine methodological insight.

COMPUTE ESTIMATE — from the official repository configuration and launch path, report the number of H100s and wall-clock time for one single run (one baseline or candidate training job). Recommended: ≤ 64 H100s and ≤ 8 hours per run. The total duration of the iterative research process is not capped.

Reproduce the human recipe

The selected experiment must have a baseline reproducible directly from the original repository. Pin the repository, assets, environment, configuration, seed, command, and compute budget — then run the official recipe unchanged.

  • Compare the result with the paper or repository claim and document any discrepancy.
  • Regardless of whether the numbers match, the local rerun becomes the task-pristine human baseline used for ranking.

Package the RSI environment

Convert the experiment into a complete Harbor-format task following the provided sample: the editable workspace, immutable assets, instructions, policy constraints, resource limits, and required outputs.

Build an independent verifier and policy

Create a fixed evaluation path that checks policy compliance, loads the submitted artifact, reports raw metrics, and computes the disclosed reward. The policy must explicitly prohibit reward hacking:

  • Evaluator or reward-path modification
  • Evaluation-data leakage and hardcoded answers
  • Undeclared external artifacts
  • Violations of the registered compute or experiment budget

Validate and submit the task

Confirm that the baseline runs correctly, the task supports meaningful improvement, and the verifier catches policy violations. Validation should include strong research agents:

GPT 5.6 Sol xhigh + Codex  ·  Opus 5 Max + Claude Code  ·  Opus 4.8 Max + Claude Code
  • Contributors with GPU access can run these validations themselves — and receive greater contribution credit for doing so.
  • We can provide execution support when compute is unavailable.
  • Submit the complete Harbor task together with baseline results, compute requirements, and the scientific rationale for the selected experiment.

See the task-contribution SOP and provided sample tasks in the GitHub org for details.

The deliverable

One complete Harbor package.

<your-task>/
├── task.toml
├── instruction.md
├── policy.yaml
├── environment/
│   ├── Dockerfile
│   └── project/      # pinned upstream source
└── tests/
    ├── Dockerfile     # clean, separate verifier image
    ├── test.sh
    └── policy_check

Alongside it

Supporting materials.

  • Baseline results — the frozen rerun of the author recipe, with any discrepancy from the published claim documented.
  • Compute requirements — H100 count and wall-clock for a single run, and the registered budget for the research loop.
  • Scientific rationale — why this experiment has a meaningful open research space, and what a genuine methodological insight would look like.
  • Author review — where possible, we reach out to the original author team to review the environment built from their project.
