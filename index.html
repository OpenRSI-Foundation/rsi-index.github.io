RSI-INDEX

RSI-Index studies how far AI research agents can improve the way models are built. We turn fully open model-development projects into auditable environments, in which an agent works to improve a real training workflow against a fixed evaluator and is scored against the original, human-written recipe.

Producing The RSI Index

In an RSI task, an agent receives the editable source for a real open project, a fixed budget, a concrete experiment, and a verifier it cannot alter. The question is not whether an agent can tune a toy proxy — but how much it can improve a human-built, open recipe while preserving the experiment's scientific contract.

What RSI-Index is

What the program is trying to find out.

RSI, self-evolve, autoresearch — different names for the same loop: an agent proposes a hypothesis, implements it, and evaluates the result against a verifiable objective. The central question is whether this loop can move beyond the best known human-designed method and reliably extend the scientific frontier.

01

Optimization, not reproduction

The agent takes over the cluster and starts from the original codebase, data, and checkpoints — then improves the pipeline to produce an artifact that outperforms the original recipe.

02

Scientific discovery, not parameter sweeping

RSI goes beyond hyperparameter search: form hypotheses, modify real model-development methods, learn from experiments, and land gains that stay meaningful under a fixed scientific contract.

03

Production scale, not toy scale

Tasks reflect problems frontier researchers care about, at model, data, and system scales where improvements matter — and transfer to real training and deployment.

The measure

How performance is measured.

RSI improvement = performance of the agent-selected final artifactmatched, task-pristine human-recipe baseline

The "human baseline" is the original authors' released recipe, rerun unchanged in the same task environment. This frozen rerun — not the paper's claim — is the ranking baseline. An independent verifier re-evaluates every submitted artifact; hard policy violations fail closed to a reward of zero.

Anatomy of a task

How a task is packaged and verified.

The environment gives the agent the actual project it must improve — pinned source, declared read-only assets, a reproducible launch path, and enough instrumentation to learn from experiments. The verifier runs in a separate clean image. 

<task>/
├── task.toml
├── instruction.md     # objective, setup, baseline, loop, submission
├── policy.yaml        # editable scope, locked variables, hard zeros
├── environment/
│   └── project/       # pinned author repository — the workspace
└── tests/
    ├── verifier       # separate clean image, fixed evaluation
    ├── integrity gates
    └── reward mapping # fails closed to zero

Violations that zero the reward

  • Reward-path tampering. Modifying or bypassing the reward path.
  • Eval leakage. Training on, filtering on, or hardcoding evaluation examples.
  • Budget overrun. Exceeding registered compute or wall-clock limits.

The verifier compares the candidate workspace against a clean pinned checkout, rejects protected-path changes, and applies programmatic and LLM-as-judge integrity checks before any metric is computed.

Collaboration

How we work with labs and original authors.

FRONTIER LABS

Compute partnerships

We are actively seeking partnerships with frontier AI labs that can provide the computational resources needed to scale RSI task design and validation.

ORIGINAL AUTHORS

Environment review

For every open project we build on, we invite the original author team to review the corresponding RSI environment — so each task is verified by the people who built the recipe it measures.
